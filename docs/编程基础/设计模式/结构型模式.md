# 结构型模式

关注如何将对象和类组装成较大的结构，同时保持结构的高效性和灵活性。

## 1. 适配器模式（Adapter）

将一个类的接口转换成客户端希望的另一个接口。

*   **要素**：
    *   **目标接口**：如 `handleInput` 方法。
    *   **源接口**：如 `pressKey` 和 `pressButton` 等不同的方法。
    *   **适配器**：`KeyboardAdapter` 和 `GamepadAdapter` 子类。
*   **其他应用场景**：对接策划表格。
*   **优点**：
    *   符合单一职责原则和开闭原则。
    *   灵活，可以非常方便的增删已有的适配器。
*   **缺点**：
    *   引入更多的类，增加代码理解难度。
    *   在源接口差异不大时，可以考虑从源接口抽象出一个基类来替代适配器的功能。

## 2. 桥接模式（Bridge）

将抽象部分和实现部分分离，使他们可以独立变化。

*   **要素**：
    *   **抽象层（只描述规则）**：
        1. 抽象类：如 `Shape` 类
        2. 扩展抽象类：如 `Circle` 和 `Rectangle` 类
    *   **实现层（实现具体功能）**：
        1. 实现类接口：如 `Renderer` 接口类
        2. 具体实现类：如 `OpenGLRenderer` 和 `DirectXRenderer` 类
*   **与抽象工厂模式的区别**：
    *   **工厂模式**：关注如何创建对象，根据不同的条件动态创建不同的产品。
    *   **桥接模式**：使抽象和实现分离，两部分可以独立变化实现解耦。

## 3. 组合模式（Composite）

将对象组合成树形结构以表示“部分—整体”的层次结构。

*   **要素**：
    *   **组件**：定义所有叶子节点和复合节点共有的接口。
    *   **叶子节点**：最终执行操作的基础对象或终端元素，不包含子对象。
    *   **复合节点**：包含一个或多个子对象的节点，提供对子树的管理接口。
*   **核心思想**：有了这些结构，客户端代码就只需要和最顶层交互，而不关心它是由哪些子对象构成。
*   **扩展**：
    *   **Godot引擎**是对组合模式实践的典范，所有可发挥实际功能的对象，都是 `Node` 节点或它的子类，可以通过搭建场景树，来组合不同的游戏场景。此外 Unity 等众多游戏引擎，在场景管理时也使用了类似的设计。
    *   **ECS（Entity Component System）**：设计上借鉴了组合模式，其强调数据驱动的设计，实体并不能像组合模式一样拥有子对象，它只是一个不包含任何行为的标识符。而组件是独立的数据，同样不包含行为，而系统则只拥有行为，不保存数据。ECS 可以看做是使用数据定义实体的一种理念，关注性能优化和行为分离。而组合模式强调的是层次结构和对象组织。

## 4. 装饰器模式（Decorator）
动态的给一个对象添加额外的职责。

## 5. 外观模式（Facade）
为复杂的子系统提供一个简化的接口。

## 6. 享元模式（Flyweight）
通过共享对象来优化大量的细粒度对象。

## 7. 代理模式（Proxy）
为其他对象提供代理以控制对该对象的访问。
