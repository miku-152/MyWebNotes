# 结构型模式

关注如何将对象和类组装成较大的结构，同时保持结构的高效性和灵活性。

## 1. 适配器模式（Adapter）
将一个类的接口转换成客户端希望的另一个接口。

**要素：**
1. 目标接口：如handleInput方法。
2. 源接口：如pressKey和pressButton等不同的方法。
3. 适配器：KeyboardAdapter和GamepadAdapter子类。

**其他应用场景：** 对接策划表格。

**优点：**
1. 符合单一职责原则和开闭原则。
2. 灵活，可以非常方便的增删已有的适配器。

**缺点：**
1. 引入更多的类，增加代码理解难度。
2. 在源接口差异不大时，可以考虑从源接口抽象出一个基类来替代适配器的功能。

## 2. 桥接模式（Bridge）
将抽象部分和实现部分分离，使他们可以独立变化。

**要素：**
1. **抽象层**：只描述规则
   - 抽象类：如Shape类
   - 扩展抽象类：如Circle和Rectangle类
2. **实现层**：实现具体功能
   - 实现类接口：如Renderer接口类
   - 具体实现类：如OpenGLRenderer和DirectXRenderer类

**与抽象工厂模式的区别：**
- 工厂模式：关注如何创建对象，根据不同的条件动态创建不同的产品。
- 桥接模式：使抽象和实现分离，两部分可以独立变化实现解耦。

## 3. 组合模式（Composite）
将对象组合成树形结构以表示“部分—整体”的层次结构。一句话说得好：“组合优于继承”。

**要素：**
1. 组件：定义所有叶子节点和复合节点共有的接口。
2. 叶子节点：最终执行操作的基础对象或终端元素，不包含子对象。
3. 复合节点：包含一个或多个子对象的节点，提供对子树的管理接口。

有了这些结构，客户端代码就只需要和最顶层交互，而不关心它是由哪些子对象构成。

**扩展：**
Godot引擎是对组合模式实践的典范，所有可发挥实际功能的对象，都是Node节点或它的子类，可以通过搭建场景树，来组合不同的游戏场景。此外Unity等众多游戏引擎，在场景管理时也使用了类似的设计。

ECS（Entity Component System）：设计上借鉴了组合模式，其强调数据驱动的设计，实体并不能像组合模式一样拥有子对象，它只是一个不包含任何行为的标识符。而组件是独立的数据，同样不包含行为，而系统则只拥有行为，不保存数据。ECS可以看做是使用数据定义实体的一种理念，关注性能优化和行为分离。而组合模式强调的是层次结构和对象组织。

## 4. 装饰器模式（Decorator）
在不改变原始对象结构的情况下，动态的为这个对象添加额外的功能。

**要素：**
1. 组件：定义统一接口，如Character类。
2. 具体组件：实现具体功能的类，如BasicCharacter类。
3. 装饰器：继承自组件并持有组件对象，如CharacterDecirator类。
4. 具体装饰器：实际实现装饰功能的装饰器子类，如AttackPowerDecorator类。

**其他应用场景：**
1. 权限管理系统：控制用户的增删改查。
2. 游戏输入系统：实现抖动过滤、坐标转换等功能。
3. 数据加密解密：数据传输过程中压缩、加密和协议封装。

**优点：**
1. 无需创建新的子类就可以扩展对象行为
2. 灵活，可以在运行时动态添加删除对象行为。
3. 单一职责，可以拆分多个装饰器共同完成复杂行为。

**缺点：**
1. 删除特定装饰器较为困难。
2. 确保装饰器效果不会因为顺序受影响。

## 5. 外观模式（Facade）
又叫做门面模式，为复杂的子系统提供一个简化的接口，来减少客户端和子系统之间交互的复杂性。

**要素：**
1. 外观类：提供统一的接口，供客户端调用。
2. 子系统：实现具体业务逻辑的类，包含了系统的核心功能。

**优缺点：**
1. 优点：简明，同时让代码独立于复杂子系统。
2. 缺点：可能会成为与所有类都耦合的上帝对象。

## 6. 享元模式（Flyweight）
通过共享多个对象所共有的状态，来让有限的内存容量中载入更多对象。来优化大量的细粒度对象。

**要素：**
1. 享元：多个对象所共有的数据或状态，如BulletFlyweight类。
2. 享元工厂：对已有的享元缓存池进行管理，如BulletFactory类。
3. 上下文：每个对象所独有的状态，如Bullet类。

**其他应用场景：**
1. 瓦片系统：对单个瓦片对象所使用的纹理、属性进行共享。
2. 粒子系统：对粒子系统使用的纹理材质，以及运动规则等数据进行共享。

一言以蔽之，所有大量对象的内存优化，都首先考虑一下是否可以用享元的思想来解决，将繁重的或者相同的部分抽象成“单例”，实际的对象只持有差异。

**缺点：**
1. 更新上下文可能需要牺牲执行速度。
2. 代码结构会因此变得复杂，单个对象的功能由多个对象组合完成。

## 7. 代理模式（Proxy）
为其他对象提供代理以控制对该对象的访问。

**要素：**
1. 服务接口：代理类伪装所必须遵守的规则，如IChunk纯虚类。
2. 实际服务：实际用于提供业务逻辑的类，如RealChunk类。
3. 代理：包含实际服务对象成员，代理完成任务，如ChunkProxy类。

**其他应用场景：**
1. 延迟加载：如大型开发游戏中，对地图区块的动态加载。
2. 资源缓存：对音频、模型等繁重资源对象进行代理，避免重复从文件或服务器中获取。
3. 权限控制：在多人联机游戏中，对玩家的行为进行校验，判断是否有权限执行。
4. 远程代理：远程过程调用（RPC），将客户端和服务端的通信简化为本地对象调用。
5. 智能代理：为已有的业务添加日志监控性能记录等功能。

**优点：**
1. 可以在客户端毫无察觉的情况下控制服务对象。
2. 实现对实际服务对象生命周期的智能管理。
3. 代理类可以在服务对象还未准备好或不存在时正常工作。

**缺点：**
1. 在服务没有正常起作用时，调试多了一个维度。
2. 实际服务的响应可能会有延迟。
