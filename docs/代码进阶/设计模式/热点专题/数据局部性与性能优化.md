# 数据局部性与系统性能优化

算法的复杂度与程序的运行时间并没有绝对关系。在游戏运行过程中，我们通常需要遍历场景中所有的游戏对象，执行更新或是渲染逻辑，此时系统的时间复杂度是无限趋近于 O(n) 的线性时间复杂度。

根据摩尔定律，处理器的性能约每两年翻一倍，但内存的效率提升显然没有这么高效。当程序运行时，设备的处理器需要不断地与内存中的数据产生交互，这就导致了处理数据的速度会大于获取数据的速度。

在游戏的运行过程中，我们通常会尽可能避免主线程中产生与硬盘 IO 交互的阻塞行为，又或者在优化渲染性能时，通过缓冲等一系列机制，尽可能减少与显卡 IO 的交互次数。而 **CPU 与内存之间的 IO 代价，我们却常常忽略掉**。如果我们能较大地减少缓存和内存交换的频率，便能带来极强的优化效果。

## 缓存命中

如果我们操作的数据是连续的，将一段数据从内存中搬运到 CPU 缓存后，其中包含着接下来数个操作所需要的数据，那么 CPU 便无需再次与内存进行读写，而只和自身的高速缓存交互，这就避免了 IO 的通信延迟，提高了总体的数据处理效率。

## 传统 OOP 组织方式的问题

开发过程中，比较常见的代码组织方式是这样的。

```cpp
class GameObject
{
    virtual void on_update() = 0;
    virtual void on_render() = 0;
};

class Player : public GameObject
{
    void on_update() override {}
    void on_render() override {}
};
```

面向对象软件架构的最大特征就是抽象化，我们通常对代码进行分块和解耦，来让它们易于修改。但是从数据局部性的视角来看，我们既要检索对虚表的追踪，来执行实际重写的子类逻辑，在完成一个接口的功能时，通常还要使用散落到各处的指针，那么这就极大地影响了缓存命中。

## 数据局部性友好的拆分

如果用以下这样的代码拆分游戏功能。

```cpp
struct UpdateComp
{
    // 执行更新功能的组件
};

struct RenderComp
{
    // 执行渲染功能的组件
};

std::vector<UpdateComp> update_comp_list;
std::vector<RenderComp> render_comp_list;

class GameObject
{
    int idx_update_comp;
    int idx_render_comp;
};
```

把所有的更新逻辑封装到更新组件中，渲染逻辑封装到渲染组件中，而游戏对象只持有他们的引用。在游戏对象更新的过程中，不直接调用游戏对象的更新方法，而是遍历不同组件存放的数组，依次执行组件的更新逻辑。这种思路可以极大地提高缓存命中的可能，是对 CPU 性能非常友好的了。

## 谨慎使用

任何优化思想或设计模式都不可以滥用。可以看出，数据局部性友好的系统设计下，有些思路是不太符合开发者直觉的，可能会使原本抽象的代码和功能需求更加抽象。

如果想要使用这种思路进行优化：

1. 首先要确保应用场景是否合适，譬如大量粒子对象更新等情况下就可以考虑。
2. 再者是通过性能分析工具，确定系统的性能问题确实是这个原因导致的，再考虑着手进行调优。

因为考虑数据局部性的优化往往会触及到整个程序最底层的架构，所以最好是有预见性地在合适的应用场景中考虑使用这种思想，而不是亡羊补牢的补丁。
