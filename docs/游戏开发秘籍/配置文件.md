# 配置文件

## 数据库 VS 配置文件

**数据库**

配置文件基本上只会用于静态数据的存储，这些数据在游戏启动时便一次性加载解析到内存中，运行时无需频繁的 I/O 操作，全程只读不可写，可以避免数据库的连接开销。

**配置文件**

数据库删除处理频繁读写的动态数据，用它来处理多读少写的情景会有性能浪费，且无论通过网络向服务器请求数据、或是在本地部署小型数据库，在移动端、主机等性能敏感的平台上都算不上很好的方案。（SQLite 算是一种轻量的数据库引擎，但是可读性相对于非二进制配置文件要差一点。）

---

## 写死在代码中 VS 配置文件

**写死在代码中**

小型项目当然是可以的。

**配置文件**

工业级的游戏项目中的属性数据通常是由专门的数值策划人员集中安排处理的，那程序就要给他们安排一套适合频繁修改和变动版本更新的数据存取框架，让其配置的不同类型数据都能直接导入到程序中进行动态解析。此外若直接将各种数据绑定在代码中，当游戏更新时，玩家就要卸载安装进行全量更新。

---

## 配置文件的分类和选择

选择的角度无非是：**可读性、文件体积、解析速度、跨平台兼容性**。

### （1）非二进制配置文件

#### 1. INI（Initialization）

本质上是一套键值对。

```ini
[Player]
Name = John  ; 姓名
Level = 10   ; 等级
```

可以看出，INI 的语法简单、格式扁平，很难实现复杂结构的嵌套。

#### 2. XML（Extensible Markup Language）

特点是可以很高效且精准地描述层次化结构，自身语法天然适合描述树形结构。

```xml
<!-- 游戏的 UI 界面布局配置 -->
<Window id="MainMenu" width="1920" height="1080">
  <Background image="bg_main.png" />
  <Button id="StartBtn" x="800" y="500" size="200x50">
    <Text font="Arial" size="24">开始游戏</Text>
  </Button>
  <Button id="SettingBtn" x="800" y="600" size="200x50">
    <Text font="Arial" size="24">设置</Text>
  </Button>
</Window>
```

所以常在游戏或软件的界面布局，或者复杂规则的配置时常常使用 XML 或类 XML 的语言。如在 WPF 中就使用了 XAML 对界面布局进行描述；QtDesigner 中使用可视化编辑生成的 `.ui` 文件，也是基于 XML 格式的实现。

**缺点**：标签冗余造成的体积问题。

#### 3. JSON（JavaScript Object Notation）

本质也是键值对，不过加入了对数组、对象等嵌套格式的语法支持。同时由于使用经典的花括号语法，在描述相同的内容时，相较于 XML 体积更小、更适合网络传输。

```json
[{
  "interval": 1,
  "rewards": 100,
  "spawn_list": {[
    "interval": 1,
    "point": 1,
    "enemy": "Slim"
  ]}
}]
```

但 JSON 缺乏注释语法，所以当我们想添加额外的描述信息时，可能就需要通过额外的字段来引入。

JSON 常用于网络通信和游戏本地配置文件。当然其还有些变种，如 JSON5（添加了注释等使可读性更好）、BSON（二进制 JSON）等。

#### 4. YAML（YAML Ain't Markup Language）

以人类可读性为核心，支持注释，足够轻量，还能够轻松描述层级关系。

```yaml
# 游戏全局配置
game:
  name: 元素领域                      # 字符串（默认无需引号）
  version: "2.3.1-beta"               # 带特殊符号的字符串
  is_pvp_enabled: true                # 布尔值（true / false）
  max_players: 32                     # 整数
  default_volume: 0.75                # 浮点数

# 玩家角色配置（层级嵌套）
player:
  base:
    health: 100                       # 基础生命值
    attack: 25
    defense: 18
  skills:                             # 技能列表（数组）
    - name: "火焰冲击"
      type: "火系"
      damage: 40
      cooldown: 8s
    - name: "自然治愈"
      effect: "持续回血"
      heal_amount: 15/3s
```

**缺点**：这种类似 Python 的游标卡尺语法，对缩进层级要求十分严格，稍有不慎便可能解析失败。

#### 5. Lua

设计之初就是为了能更灵活地描述数据需求。

Lua 既是数据载体，又可以使用图灵完备的语法作为嵌入式的逻辑，这就允许 Lua 实现的配置文件不仅可以描述静态的常量数据，还可以让这些配置拥有动态决策的能力。

**示例程序 1：**

```lua
skill_trigger = function(target)
  return target.hp < target.max_hp * 0.3 or is_boss(target)
end
```

**示例程序 2：**

```lua
-- 角色装备配置（混合表结构）
equipment = {
  weapon = {
    name = "炎魔之刃",
    attrs = { attack = 100, fire_dmg = 50 },
    enchant = function()            -- 附魔特效函数直接绑定
      play_effect("fire_boost")
    end
  },
  armor = { "板甲", "锁甲" },        -- 数组形式
  gems = { [1] = "红宝石", [2] = "蓝宝石" }  -- 显式索引
}
```

Lua 的原生数据结构 Table 也具有十分强大的扩展性，不仅支持字典、数组等混合结构，对缩进等格式也没有严格要求。同时，Lua 天生便是为了作为嵌入式的脚本设计，虚拟机非常轻量且拥有高效的解析和检索速度。

**缺点**：过于灵活的表达十分考验程序员在程序运行时异常处理的能力，复杂的语法表达式对策划也提出了更高的门槛。

#### 6. TOML（Tom's Obvious, Minimal Language）

目标是成为"更易写的 INI，更易读的 YAML"。

```toml
# 游戏配置示例
title       = "冒险岛"
version     = "1.0.0"
debug       = true
max_players = 10000

# 服务器配置
[server]
host = "cn.example.com"
port = 8080

[server.database]
type = "mysql"
host = "localhost"
port = 3306

# 数组配置
[[maps]]
name     = "新手村"
level    = 1
monsters = ["史莱姆", "蘑菇"]

[[maps]]
name     = "魔法森林"
level    = 10
monsters = ["狼", "树精"]

# 内联表
[graphics]
resolution = { width = 1920, height = 1080 }
quality    = "high"
```

没有 YAML 严格的缩进要求，比 JSON 更好写，但嵌套较浅，深层嵌套不如 YAML、JSON 直观，目前语言支持不够成熟，在复杂数据结构或数据序列化等方面不如 JSON。

### （2）二进制配置文件

**使用场景**：对配置数据的体积，或是序列化 / 反序列化效率敏感时。

#### 1. Protobuf

有着极致的压缩效率，表达相同数据的情况下相较于 JSON 体积可减少 60%～70%，在网络同步情形下可以大大减少带宽占用和流量消耗。

同时 Protobuf 的生态十分健壮，大部分语言均有支持，可以轻松解决多引擎、多平台、多端协作的问题。此外，它还支持在不删除旧字段的情况下新增新字段，通过字段扩展机制可以完美实现热更新。

```protobuf
message SkillConfig {
  int32 skill_id    = 1;
  string skill_name = 2;
  repeated int32 effect_ids = 3;  // 技能效果列表
}
```

**缺点**：强 schema 依赖。当我们的数据结构设计发生变更时，我们需要同步更新 IDL 文件，再生成对应的 C++ 等后端代码才能接入到程序中使用。在策划频繁变更或想要支持自由修改的情景下十分不方便。

#### 2. MsgPack

设计之初目标就是实现二进制的 JSON，兼具 JSON 易用性和二进制的高效性。可以在代码中十分方便地标记对应字段，进行自动的序列化和反序列化，或者提供自定义的手动序列化逻辑。

```cpp
struct Player
{
    Vector2 position;
    Vector2 dst_position;

    MSGPACK_DEFINE(position);
};

Player player;

msgpack::sbuffer buffer;
msgpack::pack(buffer, player);

msgpack::object obj = unpacked.get();
Player server_player;
obj.convert(server_player);
```

```cpp
msgpack::object on_dump(msgpack::packer<msgpack::sbuffer>& pk)
{
    // 打包元数据
    pk.pack_array(3);
    pk.pack(runtime_id);
    pk.pack(entity_type);
    pk.pack(component_list.size());

    // 打包每个组件
    for (const auto* comp : component_list) {
        pk.pack_array(2);
        pk.pack(comp->get_type());
        comp->on_dump(pk);
    }
}
```

MsgPack 更适合对数据结构更新不那么敏感的中小型应用场景。
